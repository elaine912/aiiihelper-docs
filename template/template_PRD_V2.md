# **[專案名稱] PRD**

本文件用於承接 BRD（Business Requirements Document）並轉換為可供產品、設計、工程與 QA 執行的 PRD（Product Requirements Document）。PRD 第 1 到第 3 章必須明確對應 BRD 的業務脈絡、使用角色與核心業務需求，避免 PRD 需求脫離 BRD 已確認的範圍。

> 核心原則：PRD 說明「產品要如何支援 BRD 的業務需求」。PRD 不應新增未在 BRD 第 3 章或第 4 章出現的功能範圍；若需新增，應先回補 BRD 或標示為待確認。

## **1\. 專案目標與商業價值 (Project Overview)**

本章需承接 BRD 第 2 章「專案背景與痛點」、第 3 章「核心業務需求」與第 5 章「預期商業價值」，將業務問題轉換為產品目標、交付範圍與成功判斷方式。

建議填寫內容：

* **BRD 來源章節**：
  * BRD `2.x`：對應的背景與痛點。
  * BRD `3.x`：本 PRD 要落地的核心業務需求。
  * BRD `5.x`：本 PRD 要支援的商業價值。
* **專案目標**：說明產品需解決的主要問題，以及本期要完成的產品能力。
* **本期範圍**：列出會進入第 3 章使用者故事與第 4 章詳細規格的需求範圍。
* **不在本期範圍**：若 BRD 第 4 章有周邊業務需求，需標示哪些不納入本 PRD。
* **成功指標 / 驗收方向**：描述可驗證的結果，例如流程完成率、權限正確性、內容上架效率、操作紀錄完整性或報表可用性。

建議格式：

| PRD 項目 | 對應 BRD 章節 | 說明 |
| :---- | :---- | :---- |
| 專案背景 | BRD `2.x` | 摘要說明本專案成立原因與核心痛點。 |
| 核心目標 | BRD `3.x` | 說明本期產品需支援的核心能力。 |
| 商業價值 | BRD `5.x` | 說明完成後預期帶來的業務效益。 |
| 本期範圍 | BRD `3.x` | 列出本 PRD 會細化的需求項目。 |
| 非本期範圍 | BRD `4.x` | 列出暫不納入本期實作的項目。 |

## **2\. 使用者角色定義 (User Personas)**

本章需承接 BRD 第 1 章「使用此功能 TA」與第 6 章「利益相關者地圖」。PRD 應把 BRD 中的角色、准入條件、權限摘要與專案責任轉換為產品設計與使用者故事可引用的角色定義。

填寫時需確認每個角色至少包含「角色名稱」、「BRD 來源」、「使用目的」、「准入 / 認證條件」、「可見範圍」、「主要操作」與「限制」。若 BRD 第 3 章的流程涉及角色權限差異，PRD 第 2 章需先建立角色定義，後續第 3 章再於各情境中引用。

建議格式：

| 角色名稱 | 對應 BRD 章節 | 角色描述 | 准入 / 認證條件 | 主要需求 | 可見範圍與限制 |
| :---- | :---- | :---- | :---- | :---- | :---- |
| [角色 A] | BRD `1.x` / `6.x` | [此角色在業務流程中的責任] | [登入、驗證、名單、審核或身份條件] | [此角色需要完成的產品任務] | [可見頁面、可操作功能、不可操作限制] |
| [角色 B] | BRD `1.x` / `6.x` | [此角色在業務流程中的責任] | [登入、驗證、名單、審核或身份條件] | [此角色需要完成的產品任務] | [可見頁面、可操作功能、不可操作限制] |

檢查規則：

* PRD 第 2 章不得新增 BRD 第 1 章未定義、且未標示待確認的核心角色。
* 若同一使用者可能有多重身份，需承接 BRD 第 1 章的身份優先級或權限判斷原則。
* 若某角色只出現在 BRD 第 6 章利益相關者地圖、但不操作系統，需標示為「非系統使用者」或「專案協作角色」。
* 若角色會影響第 3 章情境，角色名稱需與第 3 章 User Stories 使用的名稱一致。

## **3\. 功能需求與使用者故事 (Functional Requirements & User Stories)**

本章需逐項承接 BRD 第 3 章「核心業務需求」中的詳細規格。撰寫方式為「先需求描述、再產出 User Story」：每個情境先以結構化需求清單承接 BRD 拆出的業務規則、角色權限與例外處理，再從需求中提煉 User Story 對照表。此三層式結構（情境摘要 → 需求清單 → User Story 對照表）確保需求完整性在前、User Story 衍生在後，適合 AM 先完成需求描述再批次產出 User Story 的工作流程。

| 層級 | 區塊名稱 | 用途 |

## **4\. 規格說明**

### **4.1 多族群帳號建立與身份管理**

* **規格說明**：
  1. 帳號申請與審核需求
     * 身份別設定
       * 平台需支援以下三種身份的獨立申請流程：
         * **HCP（醫療專業人員）**：需填寫姓名、所屬機構、專科別、執照號碼，並上傳證件供 Admin 審核。
         * **Patient（病患）**：可透過邀請連結或自助申請加入，填寫基本個人資料與同意書。
         * **Sales（業務代表）**：由 Admin 批次建立或個別新增，並分配對應轄區與可見資料範圍。
     * 審核流程
       * HCP 申請提交後，Admin 應於後台收到通知並進行人工審核（核准 / 駁回），審核結果應自動通知申請者。
     * 權限分流規則
       * 帳號審核通過後，系統依身份別自動套用對應的內容瀏覽權限與功能範圍。
  2. 用戶前台需求
     * 權限規範
       * 權限角色：HCP / Patient / Sales / Admin
       * 檢視權限：依身份別顯示對應的藥品資訊與計劃內容
       * 操作權限：Patient 可填寫計劃申請；Sales 可查看轄區報表；HCP 可下載素材
     * 視覺設計規範
     * 前台呈現畫面 & 使用者流程
  3. 管理者後台需求
     * 權限規範
       * 權限角色：Admin
       * 檢視權限：全平台帳號、素材、互動紀錄
       * 操作權限：帳號審核、素材上架、權限設定、報表匯出
     * 視覺設計規範
     * 後台呈現畫面 & 使用者流程
  4. 外部 API 串接需求
     * 串接平台：客戶端 CRM / ERP 系統
     * 串接目的：同步 HCP 清單、Sales 轄區分配資料、Patient 基本資料
     * API 規格說明

### **4.2 藥品資訊內容管理與瀏覽**

* **規格說明**：
  1. 內容分類架構
     * 藥品資訊應支援多層分類（如：疾病領域 > 產品線 > 單一藥品）
     * 每份素材需標記可見身份別（可複選）：HCP / Sales / Patient
  2. 素材類型支援
     * 文字頁面（含 Rich Text 編輯）
     * PDF 文件上傳與線上預覽
     * 圖片與影片嵌入
  3. 搜尋與篩選
     * 前台需提供關鍵字搜尋、疾病分類篩選及最新上架排序功能

### **4.3 病患支持計劃 (PSP) 模組**

* **規格說明**：
  1. 計劃列表與說明頁
     * Patient 登入後可查看現行所有病患支持計劃，每個計劃需包含：計劃名稱、適用藥品、參與資格說明、申請截止日期、聯絡窗口資訊。
  2. 線上申請流程
     * Patient 可在平台上填寫計劃申請表，Admin 可於後台查看並管理申請狀態（待審 / 核准 / 駁回）。
  3. 推播通知
     * 計劃狀態更新（核准/駁回）時，系統應自動推播通知給 Patient。
     * 用藥提醒可由 Admin 設定固定週期發送。

## **6\. 非功能性需求 (Non-Functional Requirements)**

* **系統需求**
  * 平台應支援主流瀏覽器（Chrome、Safari、Edge 最新版本）及行動裝置（iOS / Android）。
* **資安需求**
  * 所有資料傳輸需使用 HTTPS 加密；含個人資料的欄位（如病患姓名、聯絡方式）需進行儲存加密，並符合當地個人資料保護法規。
* **流量需求**
  * 平台需支援三大族群同時上線操作，初期預估並發使用者數量待客戶確認。
* **權限需求**
  * 各身份別的功能權限需集中於後台設定，Admin 可隨時調整無需重新部署。
* **穩定性**：平台正常運作時間（Uptime）需達 99.5% 以上；若發生服務中斷，應於 2 小時內恢復並通知相關團隊。
* **擴充需求**：內容分類架構與身份別設計應具備擴充彈性，未來若需新增族群類型或計劃模組，應能在最小改動範圍內完成。

## **7\. 驗收標準 (Acceptance Criteria, AC)**

*此部分將作為開發與客戶驗收的最終檢查清單。*

* **核心需求**
  * **多族群帳號管理**
    * **AC 1：身份驗證正確性**
      * HCP 申請帳號時，若未上傳執照文件，系統應阻擋提交並顯示提示訊息。
      * Admin 核准帳號後，HCP 應於 5 分鐘內收到通知並可正常登入。
    * **AC 2：權限分流正確性**
      * Patient 帳號登入後，不得看到標記為「僅限 HCP」的藥品詳細資訊頁面。
      * Sales 帳號僅能查看其被分配轄區內的 HCP 與 Patient 資料。
  * **藥品資訊內容**
    * **AC 3：內容上架正確性**
      * Admin 上架素材時，若未設定可見身份別，系統應提示必填並阻擋儲存。
      * 素材上架後，對應身份別的使用者應於 10 分鐘內可於前台看到新內容。
  * **病患支持計劃**
    * **AC 4：申請流程完整性**
      * Patient 完成計劃申請表提交後，Admin 後台應即時收到新申請通知。
      * 申請狀態更新後，Patient 應透過推播通知或站內訊息獲知結果。
* **錯誤處理**
  * 系統異常時應顯示友善的錯誤頁面，並記錄錯誤日誌供技術團隊排查。
