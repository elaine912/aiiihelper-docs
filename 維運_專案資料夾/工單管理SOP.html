01
Step 1. 基礎設定與連動

在 類神經小幫手 3.0 裡，目前主要支援 LINE 客服群組 的功能唷。如果想讓 AI 類神經小幫手判斷 Bug 資訊，可以參考以下幾個小步驟：

📌 新客戶開發/上線前置作業：
  • 如果是首次建立的客戶，再麻煩將該客戶的群組名稱與對應的 Repo 提供給 Elaine 設定唷。若未完成此流程，AI無法順利判別訊息，也會找不到該群組唷。
  • 如果客戶需要類神經小幫手的協助，請跟 Elaine 說，會一起安排小幫手夥伴來協助唷。

情境：有 LINE 群組

  • (a) 與客戶建立一個 LINE 群組。
  • (b) 邀請 類神經小幫手 3.0 加入群組。
  • (c) 在群組內 Tag (標記) 小幫手。
  • ⚠️ 小提醒：目前官方帳號要透過手機版才能進行 Tag 唷。
📋 欄位設定指引：
  • 1. Group ID *：選擇指定的 LINE 群組
  • 2. 群名 (顯示用)：與 LINE 群組名稱同名
  • 3. 客戶 customerCompany：依照客戶名稱呈現 (例如：NNHCP)
  • 4. 專案名稱 projectName：依照專案名稱 (例如：NNHCP)
  • 5. Tenant ID：請輸入「tenant_aiii」
  • 6. Channel Type：請選擇「line (LINE 群、webhook 自動建單)」
  • 7. Repos：客製化 Repo 放置位置
  • 8. Modules：點擊右側「多選 module」選取公版 Repo
  • 9. 主要 AM：下拉選擇負責的 AM 名稱

情境：無 LINE 群組 (如：Email/Teams)

若客戶沒有加入 LINE 群組（例如透過 Email 或 Teams 回報 Bug），也可以走手動建單流程唷：

  • (a) 參考上述步驟，先幫客戶創立一個 模擬的虛擬 LINE 群組。
  • 這步是為了讓手動建單時有虛擬模組可以選取，就能順利建立 Ticket 了。
📋 欄位設定指引：
  • 1. 群名 (顯示用)：建議以「客戶名稱 X 回報形式」命名 (例如：禮來 X E-mail)
  • 2. 客戶 customerCompany：依照客戶名稱呈現 (例如：NNHCP)
  • 3. 專案名稱 projectName：依照專案名稱 (例如：NNHCP)
  • 4. Tenant ID：請輸入「tenant_aiii」
  • 5. Channel Type：請選擇「teams (Teams 客戶)」或「manual (其他手動建)」
  • 6. Repos：客製化 Repo 放置位置
  • 7. Modules：點擊右側「多選 module」選取公版 Repo
  • 8. 主要 AM：下拉選擇負責的 AM 名稱
  • 9. 勾選：「📧 這是非 LINE 客戶 (Teams / E-mail / 手動建群)」

Step 2. 人員身分識別 可略過

因為 AI 有時候還不太分得清楚誰是夥伴、誰是客戶，需要大家幫忙點點手協助一下唷。

操作流程

操作路徑：左側選單 > Staff

  • (a) 如果客戶曾在群組溝通，或是有新夥伴加入，可以透過 Staff 功能 看看曾經發言的人員。
  • (b) 確認身分後，如果是同事夥伴，別忘了按下 「加入」，將他們加入我們的平臺系統唷。
03
Step 3. 訊息識別分類

目前分為兩個小路徑唷：

情境 1：LINE 群組 (已加入小幫手)

工單模組在什麼情況下會建立 Ticket 呢？主要有這兩種情境：

  • (a) 當客戶 Tag 小幫手 的時候
    備註：系統會在 LINE 群組自動幫你建工單唷
  • (b) 當 AI 透過機器學習判別內容有可能是 Bug 時
    備註：如果想讓客戶看到追蹤狀況，可以到 Ticket 內頁點擊「🔔 推狀態卡片提醒」唷
💡 如果是第二種「AI 判別」的情況，我們可以回到工單管理平臺來找該則訊息：
• 在 第一頁內容 先標示為 BUG，陪 AI 一起學習。
• 進入 第二頁內頁 後，將狀態標示為 確認為 Bug ，系統就會幫你在 GitHub 建立 Issue 囉。

情境 2：手動建單流程

  • (a) 進入工單管理模組，點擊右邊的 「手動建單」 流程。
  • (b) 選取在 Step 1 創立的虛擬模組，就能順利建立 Ticket 了。
📌 溫馨提醒：剛建好時是一張 Ticket，尚未確認是 Bug。如果確認是 Bug，同樣要 進入內頁點選「確認為 Bug 」，才會正式通報到 GitHub 唷。
補充：工單判別 (第一層學習)

操作：工單管理 > 針對訊息點選標籤，讓我們一起幫 AI 變得更聰明。

Step 4. GitHub 建單與同步

如果要建立 GitHub 工單，我們可以進入該則訊息的內頁來處理唷：

📌 小提醒：要在 Ticket 內頁將狀態標示為 🐛 是 bug 系統才會自動建立 GitHub 單唷。

1. 建單流程

  • (a) 確認內容：在內層先檢查一下左側的 issue context 內容是否正確。
  • (b) 標示狀態：如果沒問題，就把狀態標示為 BUG 吧。
  • (c) 查看結果：建立完成後，可以直接點擊連結跳到 GitHub 看看唷。

2. 編輯與同步

如果發現內容需要微調，可以回到工單內層下方的 bug report 欄位進行編輯，資料會 自動同步到 GitHub 上 唷。

📌 到 GitHub 之後：再麻煩將對應的 PM 與工程師夥伴填寫在 Assignees 欄位唷。
05
Step 5. Google Chat 通報

GitHub 建立好並確認內容無誤後，再麻煩大家透過 Google Chat，依照目前的格式回報到 Bug 回報區 唷。

填單的小內容依序如下：

  • 1. 客戶名稱＋站臺：
  • 2. 回報類型：
  • 3. Bug 等級：
  • 4. 是否為客製：
  • 5. 模組：
  • 6. 是否為急件：
  • 7. 情境說明：
  • 8. GitHub連結：

(填完後附上 GitHub 連結，讓 PM 與工程師夥伴能更快了解狀況唷)
06
Step 6. 回覆排查結果

當夥伴工程師確認完狀況後，會在 GitHub 回覆排查結果。
大家除了會收到信件通知，也可以回到 GitHub 關心一下結果，並將 Issue 的狀態標記為 Done 唷。

情境 1：非 LINE 管道 (如 Email)

  • (a) 透過原管道 (如信件) 回覆給客戶。
  • (b) 回到工單系統，將狀態改為 「已結案」，讓這筆工單有個完美的 Ending 唷。

情境 2：LINE 群組管道

若是透過 LINE 群組追蹤的工單，可以參考以下流程唷：

  • (a) 將 GitHub 的 Issue status 改為 Done。
  • (b) 可以利用右上角的 「AI 建議回覆」 幫忙擬稿，確認後再用 「💬 回覆 LINE 群組」 傳送給客戶唷。
  • - 如果覺得自己回覆的內容很棒想讓 AI 學習，可以點選訊息旁的 星星 (⭐) 唷。
  • (c) 最後記得將 Ticket 狀態改為 「已結案」 唷。
⚠️ 溫馨小提醒：無論是否為 Bug，建立的 Ticket 完成後都再麻煩改成「已結案」唷，這樣下次客戶有新需求才不會被誤判為同一筆單。
